## 一、两位顾问的核心分歧

| 议题 | Kimi（产品/设计） | Codex（技术） | 我的裁决 |
|---|---|---|---|
| **栅格模型** | 2 列不变，尺寸扩为 `span{col:1-2,row:1-3}` 六种白名单；位置仍由**顺序 + dense 自动流**决定 | 4 微列 + 显式 `{x,y,w,h}` 坐标；位置由用户显式决定 | **采纳 Codex 的显式坐标**。理由见 §二 |
| **是否新开模式** | 在现有 GRID 上扩展 | 旧 LIST/GRID 冻结，新增独立 BENTO 模式（nullable 列，零回填） | **采纳 Codex**：存量页面零风险是硬要求 |
| **移动端编辑** | 不拖拽，改「点选跨度」+ 底部弹层 | 长按把手拖 + 底部 sheet preset + 四方向按钮 | **合题**：以 Kimi 的「点选为主」为默认路径，Codex 的长按拖为进阶路径 |
| **护栏** | 吸附 + 一键整理 + 可忽略的丑陋提示 | 类型最小尺寸 + 溢出检测 + 阻断发布（仅操作控件被裁时） | **两者叠加**，但阻断只保留 Codex 那一条（二维码/按钮被裁） |
| **模板** | 迁移 + 3 个模板加横幅块「润色」 | 首发不动模板，后续做 BENTO variant 经视觉评审 | **采纳 Codex**：模板截图与选用率统计不能静默变形 |
| **杀手锏** | 🎲「换个排法」随机合规排版 | 未提及 | **采纳 Kimi**，且提升为 MVP 一等公民 |

## 二、关键裁决：为什么选显式坐标而不是纯 span

用户的原话是「自由编辑大小**和位置**」。Kimi 的 span 方案只解决了「大小」——位置仍由区块顺序加 `dense` 自动流决定，**用户把卡片拖到左上角后，新增或隐藏另一块就可能触发自动回填，位置并不稳定**（Codex §1.1 点破了这一点）。那不是「位置自由」，是「排序自由」，我们已经有了。

但 Kimi 的担忧同样成立：坐标自由 = 用户可以排出丑页面。**解法不是不给坐标，而是给坐标 + 强约束**：4 微列（内容块最小跨 2 微列 = 半宽，等价于用户感知里仍是「半宽/通栏」两档宽度）、禁止重叠、禁止悬空（保存前自动压紧）、类型最小尺寸。用户获得真实的位置控制，但每个落点都是合法的。

## 三、最终方案

### 形态：BENTO v1（独立模式，与 LIST/GRID 并存）

- **4 微列 × 微行栅格**，`Block.placement = {x,y,w,h}` 整数坐标；375px 为唯一布局源（320-480px 同一套坐标，仅列宽变化）
- **用户感知的宽度仍是两档**（半宽/通栏），因为内容块最小跨 2 微列；4 微列的价值是让 IMAGE 可以做 1/4 宽小图，以及让通栏薄条/高块成为可能
- 禁止：绝对像素坐标、重叠、z-index、旋转、自定义列数、双端两套布局、块级视觉覆写（全部来自 Kimi 黑名单，我全部采纳）
- 身份首卡 / 吸底 CTA / 页脚锁定不参与布局（守住设计法则的固定骨架与转化唯一性）

### 数据模型：nullable 增量，零回填

```prisma
Page.bentoVersion Int?      // null=旧渲染；1=BENTO v1
Block.placement   Json?     // {x,y,w,h}；旧页为 NULL
```

存量页面与 8 个模板**一行数据都不改**；旧 LIST/GRID 渲染分支冻结（**明确不借机"修正"旧 GRID 与 grid-spec 文档的差异**——Codex 发现二者本就不一致，动它会让线上页面变形）。用户主动点「转换为自由布局」才写入，转换前预览、取消零写入，清空 `bentoVersion` 即完整回滚。

### 编辑器

- **桌面**：拖把手移动 + 边角 resize（吸附到微网格）+ 键盘方向键 + 20 步撤销
- **移动**：默认「点选」路径——选中卡片 → 底部弹层用**迷你网格示意图**选尺寸预设 + 四方向微调按钮；长按拖为进阶路径（44px 把手、180ms 长按、touch-action 隔离，避免与滚动冲突）
- **🎲 换个排法**（Kimi 提案，我提升为 MVP 一等公民）：在合法布局空间内随机生成合规排版，一键撤销。它是「不撞脸」诉求的最短路径，成本远低于拖拽，且天然免疫丑版式
- **✨ 一键整理**：消除孤洞、超限大块降级、恢复推荐节奏

### 公开页渲染

服务端纯函数算好矩形 → 每块输出 4 个 CSS 变量 → CSS Grid 直出。**布局能力对公开页的框架 JS 增量为 0 字节**，内联脚本维持现状（当前 2,113 字节，预算 5KB）。非法/缺失 placement 时 first-fit 降级为通栏安全布局，绝不 500、绝不重叠。

### 顺带修复（Codex 审计发现的既有缺陷）

1. **block id 每次保存都被换掉**（`deleteMany + createMany`），导致按区块的点击归因断裂——改为 diff update/create/delete，API 回传真实 id
2. **layout 与 blocks 分两次请求保存**，中间态可能出现「已开 BENTO 但块无坐标」的公开页——合并为单请求单事务

## 四、实施拆解

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 兼容基线** | 8 模板 × 320/375/480px 基线截图；布局引擎纯函数（边界/重叠/推挤/压紧/幂等）单测；nullable 列上线 + 只读 BENTO renderer（写入口 flag 关闭） | 旧页面截图零 diff |
| **P1 MVP** | BENTO 编辑器（桌面拖 + 移动点选 + 🎲 + ✨）、转换流程、单事务保存、id 稳定化 | 转换/编辑/发布全链路；公开页 client chunk 无新增 |
| **P2 质量** | 8 模板的 BENTO variant（经视觉评审）、尺寸策略按真实热区调优、溢出提示优化 | 模板视觉终审 |
| **P3 效率** | 多选、对齐分布、布局历史、跨页套用 | — |

**MVP 要验证的**：选择自由布局的用户是否更愿意完成编辑并发布，以及溢出率/撤销率/移动端误触是否可控。埋点只加在 Studio，公开页不加。
